## ۱. مشکل — «گواهی SQL Server توسط این دستگاه تأیید نمی‌شود (TLS)»

**گزارش کاربر (لاگ واقعی Web + MAUI):**

```text
fail: Tarazin.Startup[0]      Database initialization failed (SafeDataException): گواهی SQL Server توسط این دستگاه تأیید نمی‌شود (TLS).
warn: Tarazin.Web.CredentialCleanupService[0]   Credential cleanup failed (SqlException); it will retry.
fail: Tarazin.Data.DbService[0]  SQL connection test failed (SqlException, SqlNumber=-2146893019)
warn: Tarazin.Data.DbService[0]  Data operation central/UserAuthenticate failed (SqlException, SqlNumber=-2146893019)
```

پیام ورود: «سرویس ورود یا پایگاه داده در دسترس نیست»؛ در `/diag`: «گواهی SQL Server توسط این
دستگاه تأیید نمی‌شود (TLS)» (زمان آزمون ~۱ms)؛ در MAUI: «اتصال امن پایگاه داده آماده نیست» (زمان ۰ms).

**ریشه‌یابی:**

* برنامه عمداً با `Encrypt=True; TrustServerCertificate=False` وصل می‌شود (`TarazinConnection.Resolve`،
  قانون ADR-004 — هیچ bypass گواهی‌ای در هیچ محیطی مجاز نیست).
* SQL Server محلی (`Server=localhost` در `appsettings.json`) بدون گواهی پیکربندی‌شده، گواهی
  خودامضای پیش‌فرض ارائه می‌دهد که ریشه‌اش در trust store دستگاه نیست.
* کلاینت زنجیره را رد می‌کند: `SqlNumber=-2146893019` = `0x80090325` = `SEC_E_UNTRUSTED_ROOT`
  (Schannel). `DbService.Describe` آن را به همان پیام فارسی امن نگاشت می‌کند.
* همهٔ نشانه‌های دیگر (شکست startup/init، شکست `central/UserAuthenticate`، شکست credential
  cleanup، پیام ورود و «آماده نبودن» MAUI) پیامدهای همین یک ریشه‌اند: چون اتصال issuer برقرار
  نمی‌شود، ورود و صدور credential کوتاه‌عمر برای MAUI هم ممکن نیست.

**راه‌حل (دقیقاً طبق سناریوی مستند `docs/CONNECTION_TROUBLESHOOTING.md` — بدون تغییر سیاست امنیتی):**

نصب گواهی معتبر روی خود SQL Server (CA داخلی مورد اعتماد) با نام منطبق بر `Data Source`؛
تغییر کد/رشته برای غیرفعال‌کردن اعتبارسنجی گواهی (`TrustServerCertificate` با مقدار `true`)
ممنوع است (ADR-004).

**تغییرات این نشست:**

| فایل | تغییر |
|------|-------|
| `tools/sql-tls-cert.ps1` (جدید) | اسکریپت خودکار سناریو روی ویندوز (با دسترسی Administrator): ساخت CA داخلی (یا امضا با CA سازمانی از طریق `-SigningCaThumbprint`) ← صدور گواهی TLS سرور SQL با SAN منطبق بر Data Source(ها) + hostname/FQDN/loopback ← نصب CA در Trusted Root ماشین ← فعال‌کردن گواهی روی SQL Server (همان مقدار registry که Configuration Manager می‌نویسد: `SuperSocketNetLib\Certificate`) + ری‌استارت سرویس ← تأیید با TLS handshake سخت و (در صورت دادن credential) `SELECT 1` با `Encrypt=True; TrustServerCertificate=False` دقیقاً مثل خود برنامه. حالت‌های `-VerifyOnly`، `-SkipSqlConfig`، `-SkipServiceRestart`، `-SkipTrustStore`، `-SkipCaCreation`، `-Force` و fallback به `sqlcmd -N` (بدون `-C`) دارد. خروجی `.cer`/`.pfx` در `%USERPROFILE%\Tarazin\sql-tls-certs\`. |

**نکات اجرایی برای اپراتور (خلاصه):**

```powershell
# PowerShell Administrator روی همان ماشین ویندوز:

# با credential برای آزمون کامل مثل خود برنامه:
```

«اتصال برقرار است.» بدهد. MAUI ویندوز همان trust store را استفاده می‌کند (ورود مجدد کافی است)؛
برای اندروید/دستگاه واقعی CA روی دستگاه نصب و `CredentialBroker:PublicSqlServer` روی نام موجود
در SAN گواهی تنظیم شود. در production از CA سازمانی استفاده شود، نه CA محلی اسکریپت.

## ۲. تغییر مسیر — حذف درگیری TLS به درخواست مالک پروژه

**گزارش کاربر (همان نشست، بعد از راه‌حل گواهی):** «نمی‌خوام درگیر TLS بشم و این قسمتشو
کلا حذف کن. تو سناریو هم حذف کن درگیرش نباشیم.»

**تصمیم (از گزینه‌های ارائه‌شده):** فقط اعتبارسنجی گواهی خاموش شود (`TrustServerCertificate=true`)؛
رمزنگاری کانال (`Encrypt=true`) حفظ شود. این تصمیم، بند «بدون bypass گواهی» ADR-004 را ملغی می‌کند.

**تغییرات:**

| فایل | تغییر |
|------|-------|
| `Tarazin.Data/TarazinConnection.cs` | `builder.TrustServerCertificate = true` (با حفظ `Encrypt = true` و `PersistSecurityInfo = false`) + کامنت تصمیم. |
| `Tarazin.Web/CredentialBrokerService.cs` | در پاسخ broker (`MobileSqlCredential`) همان سیاست: `Encrypt = true; TrustServerCertificate = true`. |
| `Tarazin.Maui/RemoteCredentialSession.cs` | در بازسازی رشتهٔ اتصال رمزگشایی‌شده (`FetchAndCacheEncryptedMasterCoreAsync`) و `BuildConnectionString` هر دو `TrustServerCertificate = true` شد (هم‌راستا با سمت سرور)؛ و مهم‌تر: `ValidateResponse` که قبلاً پاسخ با `TrustServerCertificate=true` را رد می‌کرد، به شرط معکوس تغییر کرد (`!credential.Encrypt || !credential.TrustServerCertificate`) — بدون این، ورود MAUI با سیاست جدید همیشه «پاسخ نامعتبر» می‌داد. |
| `Tarazin.Data/DbService.cs` | اضافه‌های نشست قبل (ثابت/helper پیام TLS) برگردانده شد؛ `Describe` به حالت قبل. |
| `Tarazin.Ui/Modules/Home/Diagnostics.razor` | هشدار راهنمای گواهی (که به اسکریپت حذف‌شده اشاره می‌کرد) حذف شد. |

| `tools/security-regression-scan.py` | سیاست اسکن هم‌راستا شد: الگوی «ممنوعیت `TrustServerCertificate=true`» حذف و غیرفعال‌سازی رمزنگاری / نصب validation callback همچنان ممنوع؛ الگوهای الزامی هر سه فایل به `= true` به‌روز شد؛ فیکسچرهای self-test هماهنگ شد. |
| `docs/CONNECTION_TROUBLESHOOTING.md` | بخش «سناریو: گواهی…» و ردیف جدول حذف شد؛ بندهای «اعتبارسنجی گواهی الزامی/بدون bypass» با سیاست جدید جایگزین شد. |

| `docs/adr/ADR-004-maui-blazor-hybrid.md` | amendment ۱۴۰۵/۰۵/۲۹ اضافه شد (تاریخچهٔ ADR بازنویسی نشد): بند «بدون bypass گواهی» ملغی، رمزنگاری الزامی، پیامدها ذکر شد. |

**پیامد امنیتی (مستندشده):** محرمانگی کانال در برابر شنود حفظ می‌شود ولی اصالت/هویت
سرور SQL احراز نمی‌شود؛ برای استقرارهای حساس باید با ریسک‌پذیری شبکه مقایسه شود.
گزارش تاریخی `docs/SECURITY_REMEDIATION_REPORT.md` دست‌نخورده ماند (سند زمان خودش).

**نتیجهٔ سناریو:** خطای «گواهی SQL Server توسط این دستگاه تأیید نمی‌شود (TLS)» دیگر نباید
رخ دهد؛ ورود Web و MAUI بدون نیاز به گواهی/اسکریپت، روی هر SQL Server (حتی با گواهی
خودامضا) برقرار می‌شود.

> یادداشت: راه‌حل گواهی نشست اول (اسکریپت + بخش سناریو) طبق همین تصمیم کاملاً حذف شد؛

## ۳. ورود MAUI — «سرویس اتصال موقتاً در دسترس نیست.» فقط با user/pass درست

**گزارش کاربر:** نسخهٔ وب کاملاً کار می‌کند. در MAUI رمزِ اشتباه → پیام صحیح
«نام کاربری یا رمز عبور صحیح نیست»، اما رمزِ درست → «سرویس اتصال موقتاً در دسترس
نیست.» (کاربر: حساب SQL طرف سرور = sa؛ در کنسول Web خطایی در لحظهٔ خطا دیده
نشد.)

**ریشه‌یابی ایستا (بدون SQL Server در sandbox):**

* تفاوت رفتار «درست/غلط» یعنی درخواست به broker می‌رسد، TLS/شبکه سالم است،
  nonce و کوئری کاربر کار می‌کند و تأیید رمز انجام می‌شود. پیام گزارش‌شده دقیقاً
  همان متنِ کد `service_unavailable` است که فقط وقتی صادر می‌شود که یک استثنای
  زیرساختیِ نگاشت‌نشده در زنجیرهٔ «پس از تأیید رمز» رخ دهد (کوئری مشتری،
  `INSERT` نشست، `CREATE LOGIN`/grantها، فعال‌سازی نشست).
* مرور کد دو ضعف قطعی‌ساز پیدا کرد:
  1. **DENYهای سرور-اسکوپ در ساخت login** (`VIEW ANY DATABASE`،
     `VIEW SERVER STATE`،`ALTER ANY LOGIN`،`ALTER ANY SERVER ROLE`) برای اجرا به
     حقوق grantor سطح `CONTROL SERVER` نیاز داشتند؛ با issuer حداقل‌مجوزِ
     مستندشده (`ALTER ANY LOGIN` + `db_owner`) هر بار **خطای 4613** می‌دادند و
     چون 4613 در نگاشت نبود، کاربر فقط پیام opaque «service_unavailable» را
     می‌دید. این DENYها صرفاً hardening روی پیش‌فرض بودند (login تازه ذاتاً
     هیچ‌کدام از آن مجوزها را ندارد).
  2. **ثبت لاگ امن ناقص بود:** شکست سازندهٔ broker (unavailable شدن سرویس)
     اصلاً لاگ نمی‌شد؛ timeout قفل خانوادهٔ نشست هم خاموش ۵۰۳ می‌داد؛ و فقط
     اولین شمارهٔ خطای SQL ثبت می‌شد در حالی‌که یک batch چندخطی می‌تواند چند
     شماره داشته باشد.

**تغییرات این نشست:**

| فایل | تغییر |
|------|-------|
| `Tarazin.Web/CredentialBrokerService.cs` | حذف چهار `DENY` سرور-اسکوپ از batch ساخت login (کامنت تصمیم درج شد). مرز امنیتی بدون تغییر: کاربر تک‌دیتابیس + نقش `tarazin_maui_runtime` + RLS؛ تنها تفاوت رفتاری: `VIEW ANY DATABASE` دیگر deny نمی‌شود (دیدن نام دیتابیس‌ها مثل هر login عادی). |
| `Tarazin.Web/CredentialBrokerService.cs` | `IsIssuerPermissionFailure` حالا **4613** («Grantor does not have GRANT permission») را هم می‌شناسد → پیام قابل‌اقدام `issuer_not_authorized` به‌جای پیام عمومی. |
| `Tarazin.Web/CredentialBrokerService.cs` | `LogSafeFailure` علاوه بر `SqlNumber`، `SqlNumbers` = همهٔ شماره‌های خطای batch را (distinct) ثبت می‌کند؛ همچنان فقط نوع استثنا و شماره‌ها (غیرمحرمانه). |
| `Tarazin.Web/CredentialBrokerService.cs` | سازنده: اگر broker unavailable شود، یک `LogError` امن (`ErrorType`) ثبت می‌شود (قبلاً کاملاً بی‌صدا بود). |
| `Tarazin.Web/CredentialBrokerService.cs` | timeout قفل خانوادهٔ نشست در `/refresh` حالا `LogWarning` امن دارد (قبلاً 503 خاموش). |
| `docs/CONNECTION_TROUBLESHOOTING.md` | دستور مجوزِ دقیق issuer (با TSQL نمونه): `ALTER ANY LOGIN` + `db_owner` — `CONTROL SERVER`/`sysadmin` لازم نیست؛ `ALTER ANY CONNECTION` (یا `processadmin`) اختیاری برای `KILL` در cleanup؛ یادداشت سازگاری دربارهٔ حذف DENYها؛ ردیف جدول «سرویس اتصال موقتاً…» به `SqlNumbers` اشاره می‌کند. |

**گام بعدی کاربر (اگر هنوز خطا ماند):** Web را در console اجرا کن
(`dotnet run --project Tarazin.Web`) تا کنسول دیده شود، ورود MAUI را تکرار کن و خط
`Credential broker ... failed (..., SqlNumbers=...)` را بفرست — شماره دقیقاً می‌گوید
کدام مرحله است. همچنین دو باینری Web و MAUI باید از همین شاخه rebuild شوند
(تغییر امروز `ValidateResponse`: پاسخ با `TrustServerCertificate=true` در بیلدهای
قدیمی MAUI همیشه «پاسخ نامعتبر» می‌داد). و ردیف مشتری MAUI باید وجود داشته باشد:
`SELECT * FROM [central].[CredentialCustomers];` — اگر خالی است پیام درستِ آن
«مشتری یافت نشد» است و باید طبق راهنما provision شود.

*نویسنده: عامل Arena روی شاخه `arena/01a01d27-projects`.*

## ۴. ساده‌سازی کامل مسیر اتصال MAUI (به درخواست مالک پروژه)

**درخواست کاربر (همان نشست):** «به ساده‌ترین روش این مشکل را حل کن: کانکشن استرینگ
داخل appsettings.json را با API به MAUI منتقل کن — فقط تو API انگریپتش کن و تو
MAUI دیکریپت کن. قوانین مزخرف را بردار و قوانین را اصلاح کن.»

**تصمیم:** مدل broker به‌طور کامل حذف شد: registry مشتری (`CustomerGuid`)،
nonce/replay، نشست bearer با `/refresh` و `/revoke`، endpoint `/encrypted`،
principalهای موقت SQL (`tz_m_*`)، lifecycle cleanup و سرویس پس‌زمینه. این‌ها همان
زنجیره‌ای بودند که ورود MAUI را شکستنی می‌کردند و هرگز روی استقرار واقعی سبز
نشده بودند.

**مدل جدید:**

```
POST /api/mobile/login  { username, password }
  → PBKDF2 روی [central].[Users] (دقیقاً همان بررسی ورود وب)
  → پاسخ: { user, encryptedConnectionString: "ENC:Base64(IV+AES-256-CBC)", database }
      کلید = SHA-256(رمز ورود) — هم در سرور مشتق می‌شود، هم در MAUI از رمز تایپ‌شده
MAUI (ApiConnectionSession): رمزگشایی فقط در RAM → DbService (همان مسیر مستقیم وب)
```

رمز اشتباه → `401 invalid_credentials` → «نام کاربری یا رمز عبور صحیح نیست.» (رفتار
قبلی حفظ شد). چون MAUI پس از ورود دقیقاً همان اتصال سرور را اجرا می‌کند، هر نصبی که
وب را سالم دارد، MAUI را هم سالم دارد — بدون مجوز اضافهٔ issuer، بدون وابستگی به
CONTROL SERVER/4613.

**فایل‌ها:**

| فایل | تغییر |
|------|-------|
| `Tarazin.Share/MobileConnectionContracts.cs` (جدید، جایگزین `CredentialBrokerContracts.cs`) | `MobileLoginRequest/Response` + `MobileConnectionError`؛ قراردادهای broker (nonce/session/credential) حذف شدند. |
| `Tarazin.Web/MobileConnectionService.cs` (جدید، جایگزین `CredentialBrokerService.cs` + `CredentialCleanupService.cs`) | تأیید PBKDF2 با dummy-hash برای کاربر ناشناخته، رمزگذاری با کلید مشتق از رمز، ZeroMemory، پاک‌سازی `PasswordHash` پاسخ، لاگ امن (نوع + همهٔ SqlNumberها). |

## ۵. جداسازی ورود از API — ورود محلی یکسان در هر دو هاست

**سؤال کاربر:** «چرا login با API باشد؟ وقتی connection string داشته باشیم، همه‌چیز با
تزریق به پروژهٔ UI قابل اجراست؛ UI در هر دو پروژه یکسان باشد و API داخل پروژهٔ Web.»

**تغییر (جایگزینی مدل نشست ۴ در همان روز):**

- `IRemoteAuthenticationService` حذف شد؛ ورود دیگر از طریق API نیست.
- interface جدید سبک `IConnectionBootstrapper` در `Tarazin.Ui` (`IsReady` +
  `BootstrapAsync(username, password, ct) → bool`): فقط bootstrap یک‌بارهٔ اتصال.
- `AuthService` حالا **در هر دو هاست دقیقاً یکی** است: PBKDF2 محلی روی
  `central/UserAuthenticate`. تنها قدم اضافهٔ MAUI: اگر اتصال آماده نیست، اول
  bootstrap صدا زده می‌شود؛ ۴۰۱ یعنی credential غلط ⇒ همان پیام وب.
- endpoint: `POST /api/mobile/login` → `POST /api/mobile/connection`؛ پاسخ دیگر ردیف
  کاربر را ندارد (`{ encryptedConnectionString, database }` فقط) چون ورود محلی انجام
  می‌شود. rate-limit policy هم «mobile-connection» شد.
- `ApiConnectionSession` حالا `IConnectionBootstrapper + ICredentialSessionRevoker +
  ISqlConnectionProvider` است (نه authenticator). net اثر: MAUI بعد از bootstrap
  بدون شبکه هم login/logout می‌کند و رفتار خطاها با وب یکی است.

**فایل‌ها:** `MobileConnectionContracts.cs` (ConnectionBootstrapRequest/Response)،
`MobileConnectionService.BootstrapAsync`، `Program.cs`، `IConnectionBootstrapper.cs`

## ۸. خطای بیلد ویندوز MAUI بعد از برگشت به MSIX (سه خطا)

**گزارش کاربر:** بیلد `Tarazin.Maui` روی `net8.0-windows10.0.19041.0` سه خطا می‌داد:

1. `CS0104`: نام `UnhandledExceptionEventArgs` بین `Microsoft.UI.Xaml` و `System` مبهم
   بود (`Platforms/Windows/App.xaml.cs` — هندلر AppDomain).
2. `MSB4018`: تسک `GenerateAppManifestFromAppx` (از
   `Microsoft.WindowsAppSDK.SelfContained.targets` نسخهٔ ۱.۵) نمی‌توانست
   `obj\Debug\...\MsixContent\AppxManifest.xml` را باز کند (DirectoryNotFoundException).
3. «`ISqlConnectionProvider` یافت نشد» در سطح Solution.

**ریشه‌یابی:**

* **CS0104:** فایل WinUI با `using Microsoft.UI.Xaml;` و implicit using ها هر دو فضای نام را
  import می‌کرد؛ هندلر AppDomain باید صریحاً `System.UnhandledExceptionEventArgs` باشد.
* **MSB4018:** بعد از حذف `WindowsPackageType=None` (ورودی ۶) اپ packaged (MSIX) شد، ولی
  `WindowsAppSDKSelfContained=true` بدون قید Configuration مانده بود. در بیلد Debug معمولی
  (بدون publish/deploy) هدف‌های packaging فایل `MsixContent\AppxManifest.xml` را تولید
  نمی‌کنند؛ تسک self-contained که قرار بود همین فایل را بخواند، زودتر اجرا شد و fail کرد.
  (در حالت unpackaged قبلی این فایل در هر بیلدی ساخته می‌شد و به همین دلیل خطا تازه ظاهر شد.)
* **خطای سوم:** پیامد حل‌نشدن ارجاع در همان TFM — و علاوه بر آن `MauiProgram.cs` و
  `ApiConnectionSession.cs` مستقیماً از نوع‌های `Tarazin.Data` و `Tarazin.Share` استفاده
  می‌کنند ولی ارجاع فقط ترانزیتو از طریق `Tarazin.Ui` بود.

**تغییر:**

* `OnAppDomainUnhandledException` نوع آرگومانش را `System.UnhandledExceptionEventArgs` گرفت.
* `WindowsAppSDKSelfContained` به شرط `'$(Configuration)' == 'Release'` محدود شد
  (Debug framework-dependent می‌ماند و VS هنگام F5 پکیج framework ویندوز App SDK را
  خودش register می‌کند؛ MSIX ریلیز مثل قبل self-contained است و به runtime جدا نیاز ندارد).
* `Tarazin.Maui.csproj` ارجاع مستقیم `Tarazin.Data` و `Tarazin.Share` گرفت (بهداشت ارجاع؛
  مصرف مستقیم نوع‌ها نباید به زنجیرهٔ ترانزیتو گره بخورد).
* `docs/WINDOWS_MAUI_LAUNCH.md` هم‌راستا شد (self-contained فقط Release + دلیل).
* توصیه: بعد از pull، یک‌بار Clean Solution/حذف `bin` و `obj` (state قدیمی unpackaged→packaged).

*نویسنده: عامل Arena روی شاخه `arena/01a01f0f-projects`.*

## ۹. خطای «IConnectionBootstrapper یافت نشد» در سطح Solution — بررسی

**گزارش کاربر:** در Visual Studio (پروژه‌ی خطا: `Solution 'Tarazin'`) خطای
`The type or namespace name 'IConnectionBootstrapper' could not be found (are you
missing a using directive or an assembly reference?)` دیده می‌شود.

**بررسی (کد درست است؛ نقص ارجاعی وجود ندارد):**

* تعریف: `IConnectionBootstrapper` (و `ICredentialSessionRevoker` و
  `SafeAuthenticationException`) در `Tarazin.Ui/Services/IConnectionBootstrapper.cs`
  با `namespace Tarazin.Services` و `public` هستند.
* مصرف‌کننده‌ها: `Tarazin.Maui/ApiConnectionSession.cs` و `Tarazin.Maui/MauiProgram.cs`
  هر دو `using Tarazin.Services;` دارند؛ `AuthService.cs` و `Diagnostics.razor`
  داخل خودِ `Tarazin.Ui` هستند.
* `Tarazin.Maui.csproj` ارجاع مستقیم به `Tarazin.Ui`، `Tarazin.Data` و
  `Tarazin.Share` دارد؛ هیچ چرخهٔ وابستگی، برخورد namespace یا نوع تکراری نیست.
* باقی‌ماندهٔ نوع‌های حذف‌شده (`IRemoteAuthenticationService` و …) هم وجود ندارد.

**ریشه‌یابی:** همان ردهٔ خطای ورودی ۸ است («نوعِ X در سطح Solution یافت نشد»)،
یعنی پیامد build/design-time یک TFM (به‌خصوص TFM اندرویدِ MAUI که در Build
Solution ساخته می‌شود) روی state قدیمیِ `bin`/`obj` — نه یک خطای کامپایل واقعی.

**راه‌حل (بدون تغییر کد):**

* بستن VS → حذف `bin` و `obj` هر ۵ پروژه (یا Build → Clean Solution) → `dotnet restore`.
* build جداگانهٔ پروژه‌ها (نه Build Solution که TFM اندروید MAUI را هم می‌سازد):
  `dotnet build Tarazin.Web/Tarazin.Web.csproj` و
  `dotnet build Tarazin.Maui/Tarazin.Maui.csproj -f net8.0-windows10.0.19041.0`.
* اطمینان از نصب workload: `dotnet workload list` باید `maui` را نشان دهد.

## ۱۰. خطای «Packaged .NET applications with an app host exe cannot be ProcessorArchitecture neutral»

**گزارش کاربر:** در Visual Studio (پروژهٔ `Tarazin.Maui` روی `net8.0-windows10.0.19041.0`):

```
Error (active)  Packaged .NET applications with an app host exe cannot be
ProcessorArchitecture neutral. Please specify a RuntimeIdentifier or a Platform
other than AnyCPU.
  → %NUGET%\microsoft.maui.core\8.0.100\buildTransitive\WinUI.targets (خط 76)
```

**ریشه‌یابی (دقیق):** خط ۷۶ `WinUI.targets` در تارگت `_GetProjectArchitecture` است
(منبع: `dotnet/maui` → `src/Core/src/nuget/buildTransitive/WinUI.targets`). آن‌جا:

```xml
<Error Condition="'$(UseAppHost)' == 'true' and '$(_ProjectArchitectureOutput)' == 'neutral'
       and '$(AllowNeutralPackageWithAppHost)' != 'true'"
       Text="Packaged .NET applications with an app host exe cannot be ..." />
```

یعنی اپ packaged (MSIX) یک app-host exe دارد که نمی‌تواند ProcessorArchitecture-neutral
باشد؛ وقتی `Platform == AnyCPU` **و** `RuntimeIdentifier` خالی باشد، معماری `neutral`
حل می‌شود و خطا می‌گیرد. `Tarazin.Maui.csproj` فقط `RuntimeIdentifiers` جمع
(`win10-x64;win10-x86;win10-arm64` — برای پروفایل‌های publish) داشت و هیچ
`RuntimeIdentifier` پیش‌فرضی برای بیلد عادی/design-time VS نمی‌داد؛ پس build بدون `-r`
(و بیلدِ design-time VS با AnyCPU) خنثی می‌ماند.

**تغییر (فقط `Tarazin.Maui/Tarazin.Maui.csproj`):**

```xml
<RuntimeIdentifier Condition="$([MSBuild]::GetTargetPlatformIdentifier('$(TargetFramework)')) == 'windows'
    and '$(RuntimeIdentifier)' == ''">win10-x64</RuntimeIdentifier>
```

فقط برای TFM ویندوز و فقط وقتی RID صریحی داده نشده؛ پس `dotnet build`/F5/design-time
به معماری واقعی x64 حل می‌شوند و `-p:RuntimeIdentifier=win10-x86|win10-arm64` و
پروفایل‌های publish همچنان همان مقدار صریح را می‌برند.

**اقدام اپراتور:** `bin`/`obj` پروژهٔ MAUI را پاک کنید (یا Clean)، سپس
`dotnet build Tarazin.Maui/Tarazin.Maui.csproj -f net8.0-windows10.0.19041.0`؛
در VS می‌توانید در Configuration Manager هم Platform=x64 بگذارید (اما دیگر اجباری نیست).

*نویسنده: عامل Arena روی شاخه `arena/01a01f1e-projects`.*
